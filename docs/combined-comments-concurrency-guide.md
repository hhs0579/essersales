# 통합 코멘트 동시 작성 시 내용이 사라지는 문제 — 해결 가이드

> **목적:** 증상·원인·해결 방향 정리.  
> **상태 (2026-07-14):** 옵션 **A 구현됨** — 저장 직전 GET + 내용 있는 칸만 merge.  
> 관련: `src/composables/useCombinedComments.js`, `src/config/combinedComments.js`, `app_settings` (`scope=combined_comments`, `kind=combined_comments`)

---

## 1. 증상

| 관찰 | 설명 |
|------|------|
| 여러 명이 거의 동시에 「저장」 | 나중에 저장한 사람 내용만 남고, **먼저/다른 사람이 쓴 내용이 통째로 사라짐** |
| 같은 날짜·다른 칸 | A는「마케팅」, B는「베스트하임」을 써도, 한쪽 저장이 다른 쪽을 지움 |
| 다른 날짜 | A는 7/13, B는 7/12를 저장해도, **늦게 저장한 쪽의 전체 스냅샷**이 DB를 덮어씀 |
| 본인 화면 | 저장 직전에는 자기 글이 보이지만, 새로고침하면 없어진 것처럼 보임 |

전형적인 **마지막 쓰기 승리(last-write-wins)** 충돌이다.

---

## 2. 현재 저장 구조 (원인)

통합 코멘트는 PostgreSQL `app_settings`에 **문서 하나**로 들어간다.

```text
scope = combined_comments
kind  = combined_comments
data  = {
  labels: ["베스트하임", "사본느리", "파워프라이스", "마케팅"],
  byDate: {
    "2026-07-13": ["…", "…", "…", "…"],
    "2026-07-12": ["…", "…", "…", "…"],
    …
  }
}
```

저장 API는 `ON CONFLICT … DO UPDATE SET data = EXCLUDED.data` 형태라, **새 JSON 전체가 이전 JSON을 통째로 교체**한다.

```text
PC-A                          서버                         PC-B
  │                             │                            │
  │── GET (byDate 전체) ───────►│◄──── GET (같은 스냅샷) ────│
  │  7/13 마케팅만 수정         │      7/13 베스트하임만 수정 │
  │── PUT (전체 byDate) ───────►│  A의로 DB 교체           │
  │                             │◄──── PUT (예전 스냅샷+B수정)│
  │                             │  B값으로 DB 교체           │
  │                             │  → A가 넣은 마케팅 사라짐  │
```

~~이전:~~ 브라우저 `store` 전체를 `toPersistPayload()`로 PUT → last-write-wins.

**현재 (A):** `saveDayComments` → 저장 직전 서버 최신 GET → `mergeDaySlotsIntoByDate`로 **해당 날짜·내용 있는 칸만** 반영 후 PUT.  
「이 날 비우기」만 `forceClearAll`로 해당 날짜 전체를 삭제한다.  
같은 칸 동시 편집(옵션 B)은 아직 없음.

## 3. 충돌이 나는 대표 시나리오

### S1. 같은 날, 다른 칸 (가장 흔함)

| 순서 | A | B |
|------|---|---|
| 1 | 7/13 로드 | 7/13 로드 (동일) |
| 2 | 마케팅 칸 작성 | 베스트하임 칸 작성 |
| 3 | 저장 → 서버에 A 반영 | |
| 4 | | 저장 → **로드 당시 스냅샷 + B 칸**으로 덮어씀 → A 마케팅 소실 |

### S2. 다른 날

| 순서 | A | B |
|------|---|---|
| 1 | 전체 hydrate | 전체 hydrate |
| 2 | 7/13만 수정·저장 | 7/12만 수정·저장(늦게) |
| 3 | | B의 payload에 **옛 7/13**이 있으면 A의 7/13이 되돌아감 |

### S3. 저장 전 hydrate 없음

페이지를 오래 열어 둔 채 저장하면, 다른 사람이 그 사이 넣은 값이 **내 예전 복사본에 없어** 통째 덮어쓰기로 삭제된다.

## 4. 해결 방향 (옵션)

공통 목표: **“내가 고친 부분만 안전하게 반영하고, 남이 고친 부분은 지우지 않는다.”**

### A. 저장 전 최신본 재조회 + 칸/날짜 단위 merge (중기·권장 균형)

**요지:** 저장 직전에 서버 최신을 GET한 뒤,

- 내가 편집한 `날짜`의 `슬롯(칸)`만 내 값으로 덮고  
- 나머지 날짜·칸은 **서버 최신**을 유지한 payload로 PUT한다.

| 장점 | 단점 |
|------|------|
| 스키마/테이블 큰 변경 없이 가능 | 같은 칸을 둘이 동시에 고치면 여전히 last-write |
| S1·S2 대부분 완화 | 저장 시 GET 1회 추가 |
| UX 유지(날짜별 4칸) | merge 규칙을 명확히 문서화해야 함 |

**완료 기준:** A가 마케팅만, B가 베스트하임만 저장해도 **둘 다 남음**.

---

### B. Optimistic locking (updated_at / version)

**요지:** GET 때 `updated_at`(또는 `version`)을 기억해 두고, PUT 시 서버 값이 바뀌었으면 **거절**하고 “다른 사람이 먼저 저장했습니다. 다시 불러와 반영하세요”를 띄운다.

| 장점 | 단점 |
|------|------|
| 조용한 덮어쓰기(데이터 소실) 방지 | 사용자에게 재작성/재병합 필요 |
| DB는 `updated_at`이 이미 있음 | 거절만으로는 merge UX가 별도 필요 |

**A와 함께** 쓰면 좋음: merge 실패·충돌 시에만 B로 알림.

**완료 기준:** 낡은 스냅샷 PUT은 409 등으로 실패하고, 화면은 최신을 다시 보여 줌.

---

### C. 저장 단위를 쪼갠다 (구조 변경 — 근본적)

**요지:** “전체 byDate 한 덩어리” 대신 더 작은 키로 저장한다.

| 세분화 | 예 | 효과 |
|--------|-----|------|
| 날짜별 문서 | `(scope, kind=combined_comments_2026-07-13)` 또는 data 키 분리 API | 다른 날 충돌 제거 |
| 칸(담당)별 | 베스트하임/마케팅마다 설정 행 | 같은 날 다른 칸 충돌 제거 |
| 작성자+칸 | `userId + date + slot` | 동시 편집에 가장 강함(권한·UI 커짐) |

| 장점 | 단점 |
|------|------|
| 동시성 경계가 데이터 모델과 일치 | API·마이그레이션·엑셀 export 수정량 큼 |
| 장기적으로 안전 | 단기 핫픽스에는 무거움 |

---

### D. 운영으로만 막기 (임시)

- 담당 칸을 사람별로 고정하고, **같은 칸은 한 명만** 저장한다고 약속  
- 저장 전 “새로고침 후 이어서 쓰기” 안내  

임시 완화만 되고, **구조적 해결은 아님**.

## 5. 권장 결정

| 우선순위 | 선택 | 이유 |
|----------|------|------|
| 1 | **A. 저장 시 최신 GET + 날짜·칸 merge** | 현 구조 유지하면서 소실 대부분 차단 |
| 2 | **B. updated_at 충돌 감지** | 같은 칸 동시 편집 시 조용한 덮어쓰기 방지 |
| 3 | **C. 저장 단위 세분화** | 팀이 매일 여러 명·여러 칸을 쓰는 게 정착되면 |
| — | D | 개발 전까지 임시 규칙 |

실무적으로는 **A + B** 조합을 먼저 하고, 이후에도 충돌이 잦으면 **C(날짜별 또는 칸별)** 로 가는 것이 안전하다.

## 6. merge 규칙 (A 구현 시 합의할 것)

### 제품 전제 (현재 팀 운용)

- 칸은 4개: 베스트하임 / 사본느리 / 파워프라이스 / 마케팅  
- **사람 4명이 칸을 하나씩 담당**한다.  
- 저장 시 **자기가 작성한(내용이 있는) 칸만** 서버에 반영한다.  
- **공란(trim 후 빈 문자열)인 칸은 저장 대상이 아니다** → 남의 글을 빈칸으로 덮거나 충돌 처리하지 않는다.  

→ 구현 목표는 “전체 byDate 통째 PUT”이 아니라  
**「이 날짜에서, 내가 채워 둔 칸만 서버 최신에 합치기 / 공란 칸은 서버 값 유지」** 이다.

### 저장 요청에 실을 것 (논리)

- `date` — 편집 중인 하루  
- `slots` — 화면상 4칸 값 (또는 비어 있지 않은 칸만)  
- (선택) `baseUpdatedAt` — 같은 칸을 둘이 썼을 때만 쓸 충돌 검사용  

### 서버(또는 저장 직전 클라이언트) merge

1. 최신 `byDate` 로드  
2. `byDate[date]`에 대해 칸마다:  
   - **내 값이 공란이 아님** → 그 칸만 내 값으로 교체  
   - **내 값이 공란** → **서버(또는 기존) 값 유지** (덮지 않음)  
3. 다른 날짜는 전부 서버 최신 유지  
4. 합친 결과로 PUT  

**같은 칸에 둘 다 내용 있음:** 운용상 없어야 함. 발생 시에만 B(거절/재로드) 검토.  
**한쪽만 내용·한쪽 공란:** 내용 있는 쪽만 반영 → 충돌 없음.

## 8. 검증 시나리오 (수정 후)

1. A=마케팅만 저장, B=베스트하임만 저장 → 새로고침 후 **둘 다 존재**  
2. A=7/13 저장, B=7/12 저장 → **양일 모두** 유지  
3. A·B가 **같은 칸**을 동시에 저장 → 정책대로 거절(B) 또는 한쪽만 남음(명시적)  
4. 저장 실패 시 입력란이 서버 최신으로 갱신되고, 잃을 내용이 있으면 경고  
5. 기간(주간) 조회·엑셀에 일별 코멘트가 빠지지 않음

## 9. 하지 말 것

- “저장을 더 자주 하면 된다”만으로 끝내기 (근본은 통째 덮어쓰기)  
- 클라이언트만 debounce하고 서버는 전체 PUT 유지 (레이스는 남음)  
- localStorage 폴백과 서버 저장을 섞어 쓰기 (PC마다 다른 복사본 → 덮어쓰기 악화)

## 11. 한 줄 요약

사라지던 이유는 **‘전체 byDate JSON’ 통째 덮어쓰기**였다.  
**A(저장 직전 최신 + 내용 있는 칸만 merge)** 는 적용됨. 같은 칸 동시 편집은 이후 **B(버전 충돌 알림)** 로 보완.
